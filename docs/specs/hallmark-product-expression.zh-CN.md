# Restork Hallmark 产品表达与视觉结构 Spec

- 状态：方案已落，等待按 H1 → H4 分阶段实现
- 日期：2026-08-14
- 范围：Dashboard、桌面壳中的 Dashboard、官网
- 不在本 Spec 内：业务路由、Core API、数据模型、权限规则与安装包格式

## 1. 为什么要做

Restork 已有清楚的功能边界，但目前的产品表达仍容易落入通用 AI Dashboard 的模板：大标题、三张等宽卡、六张功能卡、再接一个 CTA。功能不少，第一眼却很难看出它与普通聊天客户端、Agent 工作台或 Obsidian 外壳究竟有什么不同。

这轮设计不以“更炫”为目标，而是让界面直接说明 Restork 的真实工作方式：

> 一句话开始任务，过程看得见，改文件前先确认，最后得到可以继续使用的笔记、报告或演示文稿。

产品识别应来自这条工作链，而不是光效、卡片数量或架构术语。

## 2. 与现有规范的边界

本 Spec 只负责宏观结构、品牌场景与页面节奏，不重复已有规范：

- [Dashboard 设计一致性](./dashboard-design-coherence.zh-CN.md)：负责 token、间距、按钮、导航与基础组件一致性。
- [开始页克制原则](./start-page-restraint.zh-CN.md)：负责开始页只有一个主要决策，不把仪表盘搬回首屏。
- [参数、预览与产品语气](./flexibility-preview-and-voice.zh-CN.md)：负责表单自由度、预览弹层和中文语气。
- [开始页与桌面更新](./start-page-and-desktop-updates.zh-CN.md)：负责开始页行为、更新通道与桌面更新体验。

若规范冲突，以安全与功能契约优先；本 Spec 不得为了视觉效果放宽写入确认、数据出站提示或工具权限。

## 3.1 已选设计系统

这轮不再逐页临时挑风格，而是先锁定同一套产品语言：

- **Genre：Editorial Workbench**。像一本可以执行任务的研究手册，安静、具体，不过度营销。
- **官网宏观结构：Feature Stack**。左侧按真实任务分四个章节，右侧固定展示对应的真实产品画面；移动端改为一段文字紧跟一张图。
- **应用宏观结构：Workbench**。界面的主要内容是用户正在做的工作；导航、状态和操作只负责帮助完成它。
- **文档宏观结构：Long Document**。连续阅读、清楚分节，不把每一段说明重新包成卡片。
- **主题：Warm Paper / Dark Ink**。暖纸与深墨是主体，现有紫、青、橙只用于选择、信息与提醒，单屏强调色不超过约 5%。
- **字体：系统 UI 字体为主**。打字机字体只保留在 Logo、短印记和极少量英文标签；中英文混排标题不再依赖装饰字体回退。
- **表现层：Clipped Ink Bleed**。如需光效，只在开始输入、运行中和大型预览里使用被容器裁切的油墨漏印，不使用全屏极光或漂浮色块。
- **Motion：Short Reveal**。进入、状态切换、等待三类；160–240ms，优先 `opacity` 与不超过 2px 的 `transform`，`prefers-reduced-motion` 下完全静止。

这些选择只锁定共同语法，不要求所有页面长得一样。官网负责讲清产品，应用负责把事做完，文档负责让人查得到。

## 4. Hallmark 审计基线

当前宏观结构审计记录为：`3 critical · 5 major · 1 minor`。

### Critical

1. 官网存在典型生成式模板骨架：Hero → 三模式卡 → Proof → 六功能卡 → CTA。
2. 三列功能网格承担了过多产品解释，页面缺少真正的叙事顺序。
3. Dashboard 与官网都有卡片套卡片，层级依赖边框而不是信息结构。

### Major

1. 使用仿浏览器圆点等装饰性界面框，容易让产品截图失去真实性。
2. eyebrow、小标签和全大写英文出现过密。
3. 功能卡普遍采用“图标块 + 标题 + 说明”的默认模板。
4. 局部颜色和字体角色仍有临时发挥，跨平台表现不稳定。
5. 页面之间虽有统一风格，却缺少与任务阶段对应的视觉变化。

### Minor

1. 多数章节使用相似留白与密度，阅读节奏过于均匀。

目标不是删除所有卡片，而是让每一层容器都有明确职责，并把最有表现力的视觉留给最重要的产品机制。

## 5. Restork 的视觉角色

### 5.1 纸张工作台

适用：开始页、知识库、任务、报告结果、设置。

- 米白、清楚、安静，适合长期阅读与填写。
- 一层主容器即可；内部优先使用分隔线、列表、表格和留白，不重复套纸卡。
- 让用户首先看见内容和下一步动作，而不是组件边框。

### 5.2 运行暗房

适用：模型正在思考、工具正在执行、等待来源、等待确认。

- 这是语义场景，不是全局深色主题。
- 只在有运行活动的局部区域出现，可显示阶段、来源、工具、耗时与停止按钮。
- 结束后回到纸张工作台，结果进入可阅读、可复核的状态。
- 不用持续光污染；最多使用轻微漏光、网格或油墨扩散来提示“正在工作”。

### 5.3 确认印记

适用：写入知识库、修改任务、导出文件、批准外部动作。

- 清楚展示“改什么、写到哪里、何时失效”。
- 批准与拒绝是事实动作，不用口号或拟人化文案。
- 视觉可以保留印章感，但交互仍使用标准按钮、焦点态和可访问名称。

### 5.4 表现力配额

- 约 80%：安静的纸张工作台。
- 约 15%：真实产品证明，如运行暗房、审批差异、交付物预览。
- 约 5%：克制的光、动效与品牌装饰。

这是设计资源分配，不是强制像素比例。

## 6. 各页面的宏观结构

| 页面 | 第一任务 | 推荐结构 | 不应出现 |
| --- | --- | --- | --- |
| 开始 | 发起一次 Research / Study / Work | 问候与目标输入 → 任务类型 → 必要状态 | 指标墙、新闻流、功能说明墙、强光 Hero |
| 仪表盘 | 回看今天发生了什么 | 进行中 / 待确认 → 最近结果 → Daily / Radar 摘要 | 与开始页重复的大输入区 |
| 运行详情 | 判断现在做到哪一步 | 阶段时间线 → 当前活动 → 来源与工具 → 结果 | 原始 JSON 默认展开、无上限日志 |
| 审批 | 判断这次改动是否可以发生 | 目标 → 前后差异 → 影响与失效时间 → 操作 | 内部枚举、英文数据库字段、模糊的“受控”标签 |
| 知识库 | 查找并阅读本地内容 | 搜索 → 文件列表 → 独立滚动预览 | 多层卡片、横向撑破、脚本化 Markdown |
| Radar | 快速判断什么值得看 | 时间范围 → 条目列表 → 稍后阅读 / 研究 / 忽略 | 无限长卡片、无来源的趋势结论 |
| 交付物 | 预览并下载可用文件 | 需求摘要 → 大纲 / 页面预览 → 版本 / 模板 → 下载 | 内联展开撑长整页、假下载按钮 |
| 扩展 | 管理 Skill、MCP 与插件 | 分类与搜索 → 状态列表 → 详情抽屉 → 启用 / 停用 | 5 张并列孤儿卡、让用户编辑原始 JSON |
| 自动化 | 看清会在何时做什么 | 已保存列表 → 新建 / 编辑抽屉 → 运行历史 → 回收站 | 手填技术 ID、隐藏配置内容 |
| 设置 | 调整产品行为 | 分组列表 → 右侧详情或抽屉 | 所有配置一次铺满、字体和颜色的任意文本输入 |

## 7. 字体、颜色与容器

### 7.1 字体角色

- UI 正文与控件：系统无衬线字体，优先各平台原生中文字体。
- 长篇阅读：同一 UI 字体，适当增大行高；不强制下载字体包。
- 打字机 / 展示字体：仅用于 Logo、极短印记、少量英文标识和品牌场景。
- 等宽字体：仅用于代码、命令、ID、哈希与技术日志。
- 中英文混排标题不得依赖 Windows 和 macOS 差异明显的装饰字体回退。

### 7.2 颜色与层级

- 所有颜色从命名 token 使用，不在渲染函数中临时写十六进制颜色。
- 一个区域原则上只有一层主边界；内部用分隔线、密度和对齐建立层级。
- 深色只服务“运行中”或“大型交付物预览”，不作为默认主题的替代品。
- 状态色固定：成功、提醒、危险、信息不得因页面而改变语义。

### 7.3 动效

- 默认时长 160–240ms，只动 `transform` 与 `opacity`。
- 每个页面最多三类动效原语：进入、状态切换、等待。
- `prefers-reduced-motion` 下取消位移、旋转与循环，只保留必要的状态变化。
- 不增加 Lottie、Three.js、远程字体或大型动效运行时。

## 8. 官网结构提案

官网不再靠功能卡枚举产品，而按一次真实任务的顺序展开：

1. **Hero 与下载**：一句定位、一个主要动作、三个真实平台下载入口；下载不藏在页面底部。
2. **开始任务**：展示开始页如何选择 Research / Study / Work 并写下目标。
3. **过程可见**：展示来源、阶段、工具与等待状态；画面来自真实 UI。
4. **写入前确认**：展示一次真实 Diff / 审批，不使用架构图替代产品画面。
5. **拿到结果**：展示笔记、日报 / 周报、PPTX / PDF 的预览与下载。
6. **信任说明**：本地数据、凭据库、沙箱、更新通道用事实列表表达，不做六宫格口号墙。
7. **文档与社区**：安装说明、GitHub、反馈入口、版本状态。

桌面端可采用“左侧四段叙事 + 右侧 sticky 真实截图”；移动端改为章节文字紧跟对应静态图，不维持 sticky。

首个公开演示固定为一条最能说明 Restork 差异的 Research 链路：

> 写下一项资料研究目标 → 查看来源与进度 → 检查准备写入的内容 → 得到一篇可以继续编辑的本地笔记。

日报、周报和 PPT / PDF 放在“拿到结果”章节作为第二条能力证明，不与首条演示争夺首屏。这样既能说明 Restork 不只是知识库外壳，也不会把十几项功能一次堆给新用户。

### 媒体要求

- 中文站与英文站分别使用对应语言的短演示，不共用错误语言素材。
- 主演示优先 MP4 / WebM；GIF 只作为兼容或分享素材，避免体积和色彩损失。
- 必须提供静态 WebP / PNG fallback；开启减少动态效果时直接显示静态图。
- 演示只用合成数据，不出现私人 Vault 路径、邮箱、API Key、用户名或真实工作内容。

## 9. 明确不做

- 不把整个 Dashboard 改成 DeepSeek Harness 的暗色网站。
- 不复制幻方或 DeepSeek 的配色、光束、图形和文案。
- 不在开始页加入宣传 Hero 或长期循环动效。
- 不引入新 UI 框架、WebGL、Lottie、在线字体服务或运行时主题引擎。
- 不用仿浏览器圆点和假窗口证明“这是桌面软件”。
- 不用架构图顶替真实产品截图。
- 不编造用户数量、效率提升、测试结果、推荐语或安全结论。
- 不因视觉改造改变现有 Core 权限、审批、隐私或数据生命周期。

| ID | 验收条件 |

| HALL-001 | Hallmark critical 从 3 降为 0；保留的 card/grid 均有明确产品理由。 |
| HALL-002 | 官网不再使用“三等列模式卡 + 六功能卡”作为主叙事。 |
| HALL-003 | 任何主要区域最多一层纸卡边界；嵌套卡需在评审中逐项说明。 |

## 11. 实施前剩余 Gate

1. H1 / H2 先做静态稿或可点击原型，并用 320–1920px 多尺寸画面验收，再改生产 UI。
2. H3 的运行暗房先在现有 Run 详情做局部、可回退的实现，不新建第二套运行界面。
3. 方向经过一次真实界面验收后，再把稳定 token、字体角色和反模式写入根目录 `design.md`；未经明确批准不提前锁死。
