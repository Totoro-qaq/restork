# Restork Hallmark 产品表达实施计划

- 状态：方案已落；按 H1 → H4 分阶段执行
- 对应 Spec：[Hallmark 产品表达与视觉结构](../docs/specs/hallmark-product-expression.zh-CN.md)
- 原则：收敛基础系统，不收敛品牌表达；结构先于装饰，真实产品先于架构图

## 1. 实施策略

改造拆成四个可以独立回滚的 PR。每个 PR 只解决一个层次，避免再次出现“UI 顺手重写、CI 全平台跑、发布又重建”的长链路。

顺序为：

1. H1：基础设计角色与反模式清理。
2. H2：官网从功能卡改为真实任务叙事。
3. H3：应用内建立运行暗房、确认印记和交付物展台。
4. H4：扩展、自动化与设置改为列表优先的管理界面。

开始页保持现有克制原则；除非单独发现缺陷，不在本计划中再次重构其信息架构。

固定设计选择：官网使用 `Feature Stack`，应用使用 `Workbench`，文档使用 `Long Document`；主题为暖纸与深墨，品牌色只作少量标记。首个官网演示固定为 Research 的“目标 → 来源与进度 → 写入确认 → 本地笔记”链路。

## 2. H1 — 基础角色与反模式

### 目标

建立跨 macOS、Windows、Linux 稳定的字体、颜色、间距和容器角色，为后续场景提供共同底座。

### 工作项

- 盘点 Dashboard 与官网的字体、颜色、阴影、圆角、边框和 z-index。
- 固定四类字体角色：UI、阅读、展示、等宽；中英文混排标题默认使用 UI 字体。
- 把临时颜色收回命名 token；消除渲染函数中的视觉常量。
- 建立“一层主容器”规则，先清理最明显的卡片套卡片。
- 删除或替换仿浏览器圆点、无意义 eyebrow、重复全大写标签。
- 给长标题、URL、命令、日志和列表项补齐统一溢出策略。
- 若用户之后明确批准锁定设计系统，再生成根目录 `design.md`；本阶段不自行创建。

### 预计文件

- `dashboard/src/styles.css`
- `dashboard/src/ui/*` 中直接输出视觉常量的少量模块
- `site/styles.css`
- `site/index.html`
- `site/zh-CN.html`

### 不做

- 不改路由、API 或数据结构。
- 不重排开始页主流程。
- 不引入字体包或新前端依赖。

### 验收

- Hallmark 重新审计；critical 不得新增。
- PostCSS / HTML 解析通过。
- 320–1920px 无页面横向溢出。
- macOS / Windows / Linux 字体 fallback 截图对比通过。
- Dashboard 仅跑相关 Vitest、typecheck 与一次生产构建，不打桌面安装包。

## 3. H2 — 官网任务叙事

### 目标

把官网从“卡片枚举功能”改为“看完一次 Restork 如何完成任务”。

### 工作项

- Hero 上方或首屏内保留三个真实平台下载入口，展示当前 Alpha 状态。
- 删除主叙事中的三等列模式卡和六宫格功能墙。
- 新增四段 proof：开始任务、过程可见、写入前确认、拿到结果。
- 桌面端采用左侧章节与右侧 sticky 真实截图；移动端一段文字配一张图。
- 制作中文与英文各自的 30–45 秒短演示，并生成静态 WebP / PNG fallback。
- 对 reduced-motion、媒体加载失败、窄屏和低带宽分别提供可用退路。
- 安全与隐私改成事实列表，链接到完整文档，不用口号代替机制。

### 预计文件

- `site/index.html`
- `site/zh-CN.html`
- `site/styles.css`
- `site/assets/` 下经过脱敏的真实截图、视频与 fallback

### 不做

- 不改下载工作流和 Release 资产命名。
- 不预先链接尚未发布的安装包。
- 不复制 DeepSeek Harness 或幻方量化的图形和配色。

### 验收

- 中文、英文站素材语言对应。
- 三个平台下载链接实际可访问，并指向已校验 Release。
- 媒体失败时仍显示静态图和说明，不出现空白大框或破图 alt。
- Tab、滚动章节和 CTA 均可键盘操作。
- 仅跑站点 HTML、链接、公开素材、语气与响应式检查；不启动 Rust、桌面或三平台打包。

## 4. H3 — 应用品牌场景

### 目标

把产品力集中在最关键的三个时刻，而不是给所有页面加光效。

### 4.1 运行暗房

- Run 发起后就地显示当前阶段，不把用户丢回列表。
- 深色区域只包住进行中的过程：模型、来源、工具、耗时、停止与等待确认。
- 完成、失败或取消后转回纸张结果；保留可折叠的完整 Trace。
- 长日志和 JSON 独立滚动，默认只展开失败步骤。

### 4.2 确认印记

- 审批页按“目标、变化、影响、期限”组织。
- 中文界面不出现英文数据库枚举和内部规则名。
- 批准 / 拒绝按钮保持标准交互与明确焦点，不用装饰替代可用性。

### 4.3 交付物展台

- 报告、PPTX、PDF 使用大弹层或专注预览，不在原页面无限展开。
- 支持页码、缩略图、键盘翻页、下载状态与错误恢复。
- 预览可使用深色展台，但编辑与配置仍回到纸张工作台。

### 预计文件

- `dashboard/src/ui/` 下 Run、审批、交付物相关模块
- `dashboard/src/styles.css`
- 必要时把视图逻辑从 `main.ts` 拆到独立 controller；不得继续集中堆叠

### 不做

- 不增加 WebGL、Lottie 或第三方动画运行时。
- 不改变审批一次性、哈希绑定或工具权限语义。
- 不将整个应用改成暗色主题。

### 验收

- 运行、失败、取消、等待审批、完成五种状态均有截图和交互测试。
- Stop / Cancel 始终可见且有效。
- reduced-motion 下等待状态仍可辨认。
- 交付物预览不会改变所属页面高度。
- 只跑 Dashboard 测试、typecheck、build 与必要的 Core contract 测试；无 API 变更则不跑全 Rust 工作区。

## 5. H4 — 管理型页面收口

### 目标

让扩展、自动化与设置像可维护的产品目录，而不是一组越加越多的卡片。

### 工作项

- Skill / MCP / Plugin：分类、搜索、状态列表、详情抽屉、启停和来源说明。
- 自动化：已保存列表、可读配置、编辑 / 暂停 / 软删 / 恢复、运行历史分页。
- 设置：左侧分组或段落索引，右侧详情；常用操作在前，高风险操作单独分区。
- 卡片多于可视区域时使用分页、虚拟列表或明确的独立滚动，不让页面无限增长。
- 统一 hover、focus-visible、loading、error、success 与空状态的下一步动作。
- 修复命令面板、列表项和状态标签的长文本布局，禁止把标签挤成单字竖排。

### 不做

- 不让普通用户输入 JSON、数据库字段或任意内部 ID。
- 不默认启用外部 MCP、网络能力或自动化任务。
- 不为了视觉整齐删除已有功能入口。

### 验收

- 100 条记录时可分页或独立滚动，操作区仍可见。
- 键盘与读屏器可以完成查看、编辑、停用、删除和恢复。
- 空状态说明为什么为空，并提供一个明确下一步。
- 中英文状态文案一致，不透传裸 `Error.message`。

## 6. 证据矩阵

每个实现 PR 至少提交以下证据：

| 类别 | 证据 |
| --- | --- |
| 设计 | Hallmark 前后审计、变更理由、保留与删除项 |
| 视觉 | 320 / 375 / 414 / 768 / 1280 / 1440 / 1920px 截图 |
| 平台 | macOS、Windows、Linux 字体与控件 fallback 截图 |
| 交互 | 键盘路径、focus-visible、Esc、焦点返回、滚动边界 |
| 动效 | normal 与 reduced-motion 两套录屏或测试 |
| 隐私 | 素材脱敏结果、公开素材扫描、无真实路径与账户信息 |
| 性能 | 无新增运行时依赖；首屏媒体有尺寸与 lazy-load 策略 |
| 回归 | 针对变更模块的 Vitest / typecheck / build；不以全平台打包代替单元验证 |

## 7. CI 与 PR 预算

本计划把“贡献者不承担发布税”写成实施门槛：

- 文档 / 官网 PR：目标 2 分钟内；只跑站点、链接、公开素材与语气检查。
- Dashboard-only PR：目标 3 分钟内；只跑 JS / TS lane。
- 单 crate Rust 变更：目标 6 分钟内；按影响范围测试，不默认全 workspace。
- macOS / Windows / Linux 安装包：只在 nightly、手动验收或 tag release 构建一次。
- 合并后的 main 不重复执行已通过的三平台发布级构建。
- 任一 PR 若因为条件 job 被 branch protection 永久等待，先修稳定聚合 gate，不用加标签强制全 CI 兜底。

## 8. 合并与回退

- 合并顺序：H1 → H2 → H3 → H4。
- 每个 PR 都必须能独立回退，不依赖下一个 PR 才恢复可用性。
- H2 可在 H1 后单独发布官网；H3 / H4 不阻塞下载页面。
- 新版安装包只在 Dashboard 与 Core 变更完成验收后发布；官网链接在 Release 资产存在并校验后再更新。
- 不在同一个 PR 混入 CI 重构、Provider 功能或数据库迁移。

## 9. 开工前 Gate

- [x] 三种产品角色已确定：纸张工作台、运行暗房、确认印记。
- [x] 官网首个演示确定为 Research 链路；周报 / PPT 作为第二结果证明。
- [ ] 先做 H1 / H2 的静态稿或可点击原型，确认后再改生产 UI。
- [ ] 明确是否授权在最终阶段生成根目录 `design.md`。
- [ ] 为四个 PR 建独立验收清单，不创建一个长达数小时的总 PR。

## 10. 完成定义

- [ ] Hallmark critical 为 0，major 均有接受或修复记录。
- [ ] 官网通过真实任务链解释产品，不靠通用功能卡墙。
- [ ] 开始页保持安静，仪表盘负责回看，运行中才进入暗房。
- [ ] 审批和交付物成为可辨识的产品场景。
- [ ] 管理型页面在长列表下仍可读、可搜索、可编辑和可恢复。
- [ ] 三平台无需安装额外字体、动画运行时或 UI 依赖。
- [ ] 文档、站点、Dashboard、Rust 与打包检查按改动范围执行，没有再次出现“一行改动等六小时”的流程。
